# `/ct-groom` — reference and design

> Text moved in full from `plugin/commands/ct-groom.md` (sub-issue #93). The command keeps the invocation, the table of exit codes and a link to this document; what follows is the reference for the spec's format aimed at whoever writes it, the detail of every validation and abort, and the history of the decisions (F5, F15, F21, F23, F32…). The slices table contract that `/ct-init` seeds into every governed repo (`docs/superpowers/CONTRATO-SLICES.md`) is the version for whoever drafts specs; this is the version for whoever runs the groom.

The invocation:

```
node ${CLAUDE_PLUGIN_ROOT}/scripts/ct-groom.mjs "<spec.md>" --repo "<owner/repo>" --milestone "<Epic>" --dry-run       # dry run first
node ${CLAUDE_PLUGIN_ROOT}/scripts/ct-groom.mjs "<spec.md>" --repo "<owner/repo>" --milestone "<Epic>" --project <n>   # and then for real
```

It is idempotent: re-running it duplicates neither the milestone nor the issues (it marks every issue with `<!-- ct-order:N -->`). **But "does not duplicate" does NOT mean "converges"**: idempotence only by existence (F5). If you fix a title or a label in the §9 table and run again, `/ct-groom` does not touch the issue already created — it reports the difference, it does not apply it by itself. See "Re-running does not converge by itself" below. (The **milestone** is not in the §9 table and is not compared: see "The scope of a groom is its epic, not the repo".)

Issues are created in `status:backlog`, never `status:ready` — it is a deliberate human gate: a human has to promote them to `status:ready` (`gh issue edit <n> --repo <owner/repo> --add-label status:ready --remove-label status:backlog`) before `/ct-next` considers them dispatchable. If `/ct-next` answers "No hay slices despachables" right after a groom, this is almost certainly why. On finishing, `/ct-groom` reminds you through stderr how many issues of the epic are still in `status:backlog` (counting the ones that already existed too: the criterion is the real state, not "I have just created something"); an epic already promoted whole, or closed, generates no reminder at all.

The **labels** the plan needs are created only if they do not already exist in the repo — before, `gh label create --force` was called for all of them on every run, and `--force` rewrites (colour and description included) an existing label. `/ct-groom` names through stderr the ones it has created as **new** and, alongside them, the ones it has **reused**; if it creates none, it says nothing. That warning is the way to detect that a spec has invented a synonym (`area:hoy` against `area:today`) instead of reusing the repo's vocabulary — which is the only thing that makes collision detection work. To see the existing vocabulary before writing the spec: `gh label list --repo <owner/repo>`.

The **dependencies** are written in the issue body as ``- merge-after `#N` ``, between backticks: `#N` is the **slice's order in the §9 table**, not an issue number, and without the backticks GitHub turns it into a link to issue number N of the repo — a false dependency that a human has no way of detecting (verified against the GitHub API: in the sandbox, `merge-after #2` of slice 3 linked to issue #2, which is slice 1's). The section carries, in addition, a line that says so explicitly. The issues created **before** this change keep the old format (`merge-after #N`, without backticks) and are still read the same way — they do not migrate by themselves; they only adopt the new format if `--reconcile` was going to rewrite that section anyway because of a real divergence.

The issue title comes from `Slice` (`#N <Slice>`), NOT from `Entrega`: `Slice` is the row's short name, `Entrega` is optional and becomes the "Descripción" section of the body. That same title is what `/ct-next` re-injects on dispatch (first line of the agent's kickoff, name of the cmux workspace) — which is why `Slice` must be short and readable, not a sentence. `Tipo` decides, on top of the `type:<valor>` label, which **technical reminder** (*addendum*) the agent receives on dispatch (`ui`/`backend`/`infra`/`bugfix`, see `scripts/kickoff.js#ADDENDA`) — a value that is none of those does not abort, but warns through stderr (the agent dispatched for that slice will receive no type addendum). Until F21, `Tipo` decided the **human gates** TOO, because the only one that existed was half a sentence inside the `ui` addendum ("gate de screenshot obligatorio"); that is no longer so — see the `Gate` column, further down.

In the `Acepta` column, **the comma always separates criteria**: an EARS criterion ("When the token expires, the system asks for login") would be split in two. It is escaped with `\,` (only that exact sequence; a lone backslash is preserved). `Protegido` is not chopped up by commas (free text in one piece), `Dep` extracts its `#N` with a regex (a comma inside makes no difference), and in `Área`/`Toca` the comma separates tokens but a token can never contain one (it is discarded on normalizing, so `\,` is of no use there).

The spec's §9 table admits two optional columns, `Área` and `Toca` (it also accepts `Area` without the accent), with comma-separated values. "No value" can be written as `–`, `-`, `—`, `−`, `--` or an empty cell (any dash variant is valid — a text editor or a phone with autocorrect can swap one for another without you noticing; all of them mean "none" in `Dep`/`Acepta`/`Área`/`Toca`/`Gate`/`Señal`):
```
| # | Slice | Tipo | Entrega | Dep | Acepta | Protegido | Área | Toca | Gate | Señal |
|---|-------|------|---------|-----|--------|-----------|------|------|------|-------|
| 1 | model | backend | users table | – | AC-1.1 | schema | api | db, migration | – | – |
| 2 | api | backend | endpoint | #1 | AC-2.1 | – | api | – | – | `api_requests_total` metric with an `endpoint` label |
```
### `Gate` — the human gates, split apart from `Tipo` (F21)

`Gate` *(optional)* declares which **human gates** have to be closed before merging that slice. **Closed** vocabulary (`scripts/gates.js`):

- `visual` — a human has to SEE the change: before/after screenshot or video in the PR;
- `apply` — nothing is applied against a real environment until a human reviews the plan/dry-run.

**The default case demands writing nothing**: `Tipo: ui` implies `visual`, `Tipo: infra` implies `apply`. The column exists for the two deviations, and `/ct-groom` **warns through stderr on both**:

- **adding** a gate that the `Tipo` does not imply (`Tipo: backend` + `Gate: visual`) — the real case that motivated the column: a migration with a backfill that moved the most visible progress bar of the epic. It received the backend addendum and no gate at all, and nothing flagged it;
- **waiving** one that it does imply, with a leading `!` (`Gate: !visual` over a `Tipo: ui` that genuinely changes nothing visible). Removing a gate is never silent.

An empty cell, or one with a "no value" marker, means *I have declared nothing*, **not** "I waive everything". A token outside the vocabulary, or asking for and waiving the same gate in the same cell, **abort** (unlike an unknown `Tipo`, which only warns): a gate that cannot be explained either to the agent or to whoever reviews would be a gate that only exists in the spec.

Where each resolved gate ends up: the issue's **`gate:<token>`** label (or **`gate:none`** if there is none — silence cannot mean both "no gates" and "issue predating the gates"), the body's **`## Gates`** section, an explicit line in the agent's kickoff, and the `gates` field of its `.agent/SLICE.md` (F22 — it used to be `.agent/STATE.md`, which is the coordinator's, not the slice's). That is why it survives a re-dispatch, a `--reopen` and a `/clear`: `/ct-next` reads it from the **issue**, not from the spec. An issue groomed before F21 (with no `gate:` label at all) falls back to the `Tipo`, so it does not lose the gate it already had.

**The loop writes and shows the gates; it does not stop you merging with one left unclosed.** The one who closes them is you.

### `Señal` — the slice's observability signal (Slice 10)

`Señal` *(optional)* declares the **observability signal** the slice promises: which metric, log or event its production code has to emit once it reaches production (e.g. "`backfill_progress` metric with an `estado` label"). Free text in one single piece, like `Protegido`: the comma separates nothing.

**The signal is not one more acceptance criterion.** The criteria in `Acepta` are functional: they say what the code has to do for the slice to be done, and the slice judge already measures them in its `estado-final` item. The signal promises something else: **what is going to be seen in production** once the slice is deployed — the metric, the log or the event by which somebody will know, without reading the diff, whether this is working. If the cell repeats an acceptance criterion in other words, the `observabilidad` item ends up measuring what `estado-final` already measured: it adds no information at all, and the epic is left without its one column that talks about *after* the merge. Practical rule: if what you have written can be checked by running the tests, it is an acceptance criterion, not a signal. And the slice judge measures it: when what the signal promises is already verified by a test of the accumulated diff and the cell names nothing that can be read in production (no metric, no log, no event), the `observabilidad` item emits a `low` finding with `señal redundante` — the item stays `conforme`, because the signal was measured; what the `low` says is that it measured what `estado-final` had already measured, and that count travels in the epic's telemetry (`findings_by_rule`).

If the slice has nothing observable to promise, the **reasoned exemption** is declared: `N/A — <razón>` (the same language as a plan's Global verification). An exemption **with no reason** (a bare `N/A`, or with the separator and nothing behind it) **aborts with exit 2** — unlike an unknown `Tipo`, which only warns: the reason is what a human approves in the groom and what the slice judge cites as `no-aplica`; an exemption nobody can read is an undeclared signal disguised as a decision.

Where it ends up: the **`## Señal de observabilidad`** section of the issue body (verbatim from the cell, only when there is something to say — signal or exemption), from there to the `senal:` field of the worktree's **`.agent/SLICE.md`** at dispatch time (`/ct-next` seeds it; absence is declared, never omitted), from there to the first **`## Señal`** section of the slice judge's package (`ct-step` pastes it, read from disk and with no agent in between), where the **`observabilidad`** item of `ct-slice-judge` measures it against the accumulated diff: that what was promised is emitted by production code, instrumented the way this repo already instruments, with no labels of unbounded cardinality. The agent's kickoff names it too when the issue declares it.

An empty cell, or one with a "no value" marker, means *I have not thought about it* — it is not an exemption: the slice judge measures its item as **`sin-vara`**, and that count travels in the epic's telemetry (`rubric_sin_vara`). If the spec does not carry the column at all, `/ct-groom` warns about the consequence: every slice of the epic will come out `sin-vara` on that item.

`/ct-groom` translates each value into `area:<x>`/`touches:<y>` labels on the issue — they are the same ones `claim.js#tokensOf` and `dispatch.js#SERIALIZING_TOUCHES` use to detect collision and force serialization. If a slice declares no `Área`/`Toca` (or the spec does not even carry those columns), no label of that kind is emitted and the collision/serialization machinery stays inert for that slice, just as before.

### `E2E` — the end-to-end journeys, and the gate DERIVED from them

`E2E` *(optional)* declares which end-to-end journeys the agent has to traverse before opening that slice's PR — the criterion by which you decide whether a slice needs one is "does the system need to be up?": not all of them carry one, and forcing one per slice would produce filler nobody reads (measured by hand over a real 8-slice epic applying that criterion: only 2 needed it). Each cell can only be in one of **three states**, over the WHOLE cell and never by prefix (a legitimate journey can begin with "no": "no access to /metrics without bringing the server up"):

- **with journey(s)** — one or several, comma-separated (same escaping rule as `Acepta`: `\,` for a comma inside the journey itself, never separating two). Each one is copied **verbatim** into the issue's `## E2E` section: it is the textual instruction the agent receives, so no paraphrasing is possible here;
- **the token `no`** (or `n/a`) — a POSITIVE declaration that this slice has nothing to traverse. Unlike `Dep`/`Acepta`/`Protegido`/`Área`/`Toca`, a dash here does NOT mean this: it means the third state, below;
- **undeclared** — an empty cell, or one with any "no value" marker (`–`, `-`, `—`, `−`, `--`). It is only a valid state if the table has **no `E2E` column** at all: a spec predating this round does not have it, and there "undeclared" is the right thing in every one of its rows. If the column IS present in the header, every row has to decide — see the first abort, below.

The human `e2e` gate **is not written in the `Gate` column**: it is DERIVED from `E2E` carrying at least one journey, for exactly what already holds for `visual`/`apply` in the opposite direction — two places can say the same thing and diverge, and here there is no way to ask for an `e2e` without saying WHAT to traverse. Writing `Gate: e2e` by hand is tolerated only when the row also carries real journeys (it warns as redundant, it does not abort: the result is identical with the `Gate` cell empty); `Gate: !e2e` over a row with journeys **aborts** (fifth abort, below), and over a row without them it warns that the waiver does nothing. The gate cannot be waived from `Gate` because nothing is waived from there: without the label, the `## E2E` section is still emitted, `/ct-next` still seeds the journeys, `ct-step` still demands the `e2e` step and `--release` still demands the correspondence. To withdraw the e2e from a row you write `no` in its `E2E` cell. Where the resolved gate ends up: the `gate:e2e` label, the `## E2E` section of the issue body (right after `## Gates`), an explicit line in the kickoff, and the `e2e` field of the `.agent/SLICE.md` that `/ct-next` seeds.

**The five aborts of this column**, all with the same shape as `Gate`'s (above: they are ALL validated before touching GitHub, `--dry-run` included, and they quote the literal cell, never just the row number):

1. **Column present and cell undeclared.** The table HAS an `E2E` column, so every row decides: a journey, or `no`. A dash here does not distinguish "it was thought about and there is none" from "nobody filled in the column" — the ambiguity the `no` token exists to remove.
2. **Contradiction in the same cell.** `no` AND a journey at once (`no, curl -i :9115/metrics`) does not pick a winner silently: you drop one of the two.
3. **`Gate: e2e` with the `E2E` cell saying `no`.** Nobody would know what to traverse — the gate is not written by hand precisely because of this.
4. **`Gate: e2e` with no `E2E` column in the table.** The same reason as abort 3, tested on its own so that abort 1 (which only applies with the column present) does not mask it: without the column, there is no journey the row could be declaring.
5. **`Gate: !e2e` over a row that declares journeys.** A waiver that waives nothing: the only consequence of removing the label is that the signal for the human disappears, while the work (issue section, `/ct-next` seed, `ct-step` step, `--release` correspondence) goes on being demanded in full. The remedy is the cell: write `no` in `E2E`.

### `## Contexto del epic` — an optional section of the spec, outside the table

Besides the table, the spec admits an optional **`## Contexto del epic`** section (outside the table, at any point of the file — it is located **by the text of its heading, not by its section number**, the same criterion by which the §9 table is located by its `Slice`+`Dep` columns: a spec's section numbers move as soon as somebody inserts something ahead of them). Its content is copied **identically into the body of every issue of the epic**, and `--reconcile` keeps it up to date if the spec changes (see "Re-running does not converge by itself", further down).

**It cannot contain anything that cuts it short**: no level-3-or-lower subheadings (`###`, `####`…) and no self-contained HTML comment (one that opens and closes `<!-- … -->` on the same line — the same "end of section" criterion that already governs the rest of the issue body's sections, see "The end of a section…" further down). Those two things, if they appear inside, do truncate: `/ct-groom` warns naming the line that cuts, and **emits the section in no issue at all**.

**Neither can it leave a delimiter unclosed**: a code fence (` ``` `) or an HTML comment (`<!--`) opened and left unclosed do the opposite of a truncation — they hide from the scanner everything that comes after, so the section stops ending where it seems to and swallows the rest of the spec, the slices table included. `/ct-groom` detects it and does not emit the section either. A **properly closed** fence is legitimate content and triggers nothing.

The four cases in which the section is not emitted (absent, empty, truncated, with an unclosed delimiter) warn **separately**, because each one is fixed a different way — and they do not mean the same thing to `--reconcile`: **absent** or **empty** say the epic has no common context, and then the section is withdrawn from the body of the issues that had it; **truncated** or **with an unclosed delimiter** say that no valid text could be read, and then nothing is touched — a formatting error in the spec does not erase the context the N issues already carry. A **level 1 or 2** heading behind the text, on the other hand, is **not** a problem: it is the section's normal ending (the same one that ends any other section of the spec) and it passes **silently** — no warning, with the context being emitted normally up to that point. Use bold text or lists inside, never headings.

### `## Decisiones congeladas` — a section of the spec template's core

Like the rest of the spec's sections, this one is governed by the template (`_TEMPLATE-execution-spec.md`, the core); just like `## Contexto del epic`, it is optional as far as `/ct-groom` is concerned and it is located **by the text of its heading, not by its section number** (outside the table). Its content is copied into the body of every issue of the epic —so that the agent implementing a slice has in front of it the epic decisions its work must respect, and pours them into `## 2. Closed decisions` of its plan—, and `--reconcile` keeps it up to date if the spec changes. **Difference from the epic context:** the provenance (`*(Procedencia: …)*`, on a single line) is stripped from each line when projecting — it is meta for whoever freezes, not for whoever executes; if the trim does not catch it, the line travels as it is and `/ct-groom` warns about it. Each decision is a bullet (`- **D-N · …** — …`); do not put headings (`###`) inside, or the section is not emitted (the same guardrail as the epic context). A spec without this section is valid.

Every issue receives in addition, always, an empty **`## Contexto heredado`** section (with a placeholder saying who fills it in and that nobody is going to overwrite it). That one is written by the coordinating session, when something already merged conditions that particular slice — and `/ct-groom` **never touches it**: it neither compares it, nor rewrites it, nor inserts it, nor deletes it. It is the place for context belonging to ONE slice; `## Contexto del epic`, by contrast, is the same text in every issue of the epic.

**And it holds up when you paste another issue's body in there**, which is exactly what is needed ("slice #2 left this set up"): that text carries the SAME headings as any issue of the epic, because the same generator writes them. `--reconcile` treats everything **between `## Contexto heredado` and `## Acceptance criteria`** as yours and does not write a single byte there — neither in the headings you paste nor in the prose you write around them. What can happen is that it **gives up**: if the body's only `## Dependencias` (or the `## Out of scope / Protected` anchor) is the one you pasted, `--reconcile` does not rewrite it **and neither does it add a second copy further down** — the dispatcher obeys the FIRST one, which would be yours. It says so through `stderr` with the concrete remedy, and it counts towards the exit code. The exception is `## Contexto del epic`: if the pasted one is the only one, its own is **inserted ahead** of your section, without touching it, and from then on it converges.

One detail worth knowing because it decides the scope of everything above: the end of your zone is marked by `## Acceptance criteria`. If that heading **does not appear exactly once** in the body (somebody renamed it, deleted it, or you pasted another copy), there is no way of knowing where yours ends — and then `--reconcile` writes **nothing** past `## Contexto heredado`, gives up out loud and tells you to restore it. It is deliberate: of the two possible errors, the expensive one is the one that erases hand-written text.

### The spec comes in frozen or it does not come in (F32)

Before even looking at the table, two checks over the WHOLE spec — the freeze gate, pre-registered in F32 as «two greps in the pass groom already makes»:

- **unresolved `[NEEDS CLARIFICATION` → exit 2.** They are allowed while the spec is in DRAFT; groom only accepts frozen specs, and freezing with a pending gap is invalid: it is resolved with whoever decides, or parked in `## Decisiones aparcadas`. The message names how many, and the line of the first one.
- **`## Hipótesis` absent or empty → exit 2.** With no falsifiable bet it is not an epic and it does not come in through groom (decision 2026-08-07); work with no bet (maintenance, bugfixes) goes as loose issues. A residual HTML comment from the template does not count as content. The *quality* of the hypothesis is judged by the human at the freeze — groom only looks at presence: being cleverer than its pre-registration would be a different instrument.

They fall together with the table errors below, TOGETHER in a single exit 2, before any mutation and also under `--dry-run`. This documents the gate here and not in the contract's block on purpose: the contract governs the table and does not grow without something being removed; the spec's sections are governed by its template (`_TEMPLATE-execution-spec.md`).

### The table is validated whole before touching GitHub

`/ct-groom` (also under `--dry-run`: a dry run that validates less than the real run is a trap) reviews the complete §9 table and **aborts with an exit other than 0**, creating nothing, if:

- it finds no §9 table at all, or it finds table(s) but no header with the `Slice` and `Dep` columns;
- the `#` header column is missing;
- there is an interruption (a blank line, or any line without `|`) halfway through the table block — it must be a single contiguous markdown block, with no gaps between rows;
- some row's `#` is not a bare integer: `1`, `2`… — never `S1` nor `**1**` (bold/backticks/letter prefixes are not tolerated here, on purpose);
- some row has fewer or more cells than the header (check for an unescaped `|` inside a cell), or the `Slice` cell is empty, carries a "no value" marker, or carries only a `#N` reference with no name around it (the issue title comes from there — see above);
- `Dep` has content that is not recognizable as `#N` (e.g. `S1` instead of `#1`) — if there really are no dependencies, write `–`;
- a `Dep` reference points at a `#` that does not exist in the table, or at the slice itself (self-reference: a slice never depends on itself).
- a `Gate` value is no known gate (the message names the whole vocabulary and the `!` waiver syntax);
- a row asks for and waives the SAME gate (`visual, !visual`) — no winner is picked silently over a human gate.

If several of these fail at once, they are **all reported together** in the same execution (you do not need to fix one, run again, and discover the next). Absent optional columns (`Tipo`/`Entrega`/`Acepta`/`Protegido`/`Área`/`Toca`) and degraded values (a `Tipo` that is no key of `ADDENDA`, a prefix in the wrong column of Área/Toca, a token that normalizes to empty) do not abort — they are warned about through stderr and the groom carries on. An absent `Gate` **does not even warn**: its absence degrades nothing (the gates are derived from the `Tipo`, as always), and a warning that comes out on every run of every spec without describing any loss is noise that trains you to ignore the rest.

### What `/ct-groom` has touched when it aborts (F15)

This is documented because the natural deduction —"if it aborts halfway, it will have left my repo half done"— is frightening, and leads to cleaning up by hand things that must not be cleaned up. What can be asserted, and what cannot:

- **Everything `/ct-groom` READS comes ahead of everything it WRITES.** Argument validation, the §9 table, resolution and verification of the link to the spec, enumeration of issues, of labels, of milestones and —with `--project`— the introspection of the Project v2 (which demands an iteration field named exactly `Sprint` and an iteration covering today). **If it aborts in any of those steps, it has created nothing**: no milestone, no labels, no issues.
  Until F15 this was **not** true for `--project`: `ensureProjectMeta()` was lazy and the first point that forced it was *after* the milestone and the labels, so "the project has no Sprint field" aborted with the milestone and the labels already created. Verified by construction against the unfixed code, with a `gh` stub that records every invocation: the log came out `milestones -f title=Epic`, four `label create`, and only then `project view`. The project block was moved forward whole, ahead of the first mutation.
- **What is NOT promised: there is no transaction.** Once validation is passed, the write order is milestone → labels → issues → registration in the Project v2 with its Sprint. A failure *there* (network, rate limit, auth down, a Ctrl-C) leaves what came before created. There is no rollback, and none is pretended.
- **You get out of a halfway abort by running again, not by cleaning up by hand.** The milestone is reused by title (all states are listed, so as not to duplicate a closed one); of the labels only the missing ones are created, and the ones that already existed are **not** touched (neither colour nor description); the issues are recognized by their `<!-- ct-order:N -->` marker and are not duplicated; and an issue that ended up created but outside the Project (an interruption between the two calls) is detected with `hasProjectItem` and added on the next run.
- **The Project's item list is read WHOLE, or it says so (F18).** `gh project item-list` is a bounded read (`--limit`), and `hasProjectItem` uses it to decide that an item **does not exist**: with the cap reached, an issue that was already in the Project was added again — **duplicates, silently**. Now `items.length` is compared against the `totalCount` that `gh` itself returns; if the cap trimmed, the query is repeated asking for exactly that total, and if it still comes back short it **aborts** instead of duplicating. With a version of `gh` that does not expose `totalCount`, it warns that truncation could not be ruled out — it is never taken as complete silently. The same with the introspection of the Project's fields (`fields(first: 50)`): if not all of them have been seen, the message no longer asserts «this project has no Sprint field», it says that it could not be checked.
- **Without `--reconcile`, an issue that already exists is never edited.** Divergences are reported through stderr and it exits `3` — nothing is written.
- **`--dry-run` mutates nothing, ever** — it does not even create the milestone. It does perform reads (including the two of the spec link's verification).

### The scope of a groom is its epic, not the repo

`/ct-groom` numbers the slices `1..N` **per epic** (one invocation = one `--milestone` = one epic) and writes that number into `<!-- ct-order:N -->`. The §9 contract says so: *«los `#` de esta tabla son únicos dentro de su milestone, no del repo»*. Since F23 that is true here too — until then it was true only in `/ct-next`, and a new §9 table starting at `1,2,3` paired up with the issues of an earlier, closed epic.

In practice: **you can start every spec's §9 table at `1`**. Two epics of the same repo do not tread on each other.

A groom only looks at the issues whose milestone is the one you passed it. Those of other epics are not paired, are not reported as a divergence and are not declared orphans. «Orphan issue» comes to mean what it says: an issue **of this epic** whose order is no longer in the §9 table.

**Direct consequence: the milestone can no longer show up as a divergence.** A paired issue always has, by construction, the milestone you asked for — it is the condition for having entered the pairing at all. If you change an issue's milestone in GitHub and run again, `/ct-groom` does **not** report it to you: depending on where you moved it, either it ignores it as belonging to another epic, or it stops dead with **exit 1** (the two situations below), or it creates a new issue for that slice — warning through stderr that it may be duplicating it. The milestone comparison still exists in `scripts/reconcile.js` (a pure module, usable by other callers), but from `/ct-groom` it is unreachable.

### The two situations in which `/ct-groom` stops dead

Both fall **before touching anything** (before even creating the milestone), also under `--dry-run`, and exit with **exit 1** saying `no se ha creado ni modificado nada`. If both coincide, both are reported and it exits a single time.

**1. An issue with no milestone whose `ct-order` collides with your §9 table.** There is no way of knowing whether it belongs to this epic (somebody removed its milestone, or the milestone was deleted in GitHub) or to another, and both possible readings do damage: pairing it would rewrite somebody else's issue, ignoring it would create a duplicate. Assign it its milestone and run again.

> An issue with no milestone whose `ct-order` does **not** collide with your table only produces a warning. It does not block, but it does not keep quiet either.

**2. A slice of yours that already has an issue in another milestone, pointing at the same spec.** It is the signature of an epic renamed in GitHub, or of a typo in `--milestone`. Without this gate, that run would see zero issues in its epic and would recreate the whole epic duplicated, with exit 0. If you renamed the epic, use its real title; if it is genuinely a new epic, its §9 table should not be pointing at the previous one's spec.

> An issue from another milestone pointing at **another** spec (or carrying no link to the spec to compare it against) does **not** stop the run: those are, normally, two legitimate epics sharing order numbers, which is exactly what this scope allows. But neither is it discarded silently — a **warning** comes out through stderr naming it with its real milestone, because that is exactly the bucket a duplicated epic would come out of if the link failed to match merely because the issue is old (groomed before F10) or because its link ended up degraded to `— sin enlace: <motivo>`. The warning comes out only when **that slice does not yet have an issue in your epic**, which is the only situation in which one is going to be created and, therefore, in which there can be a duplicate: if it already has one, there is nothing to duplicate and nothing to warn about. It does not change the exit code, and in a run that stops dead at one of the two gates it is not emitted (nothing is created there).

### Re-running does not converge by itself — it detects divergence, it does not apply it (F5)

Until this version, "idempotent" meant *existence-only*: if the `<!-- ct-order:N -->` marker already appeared in some issue, `/ct-groom` printed "ya existe, no se duplica" and moved on to the next — without looking at whether that issue's title or labels still matched what the §9 table produces today. An author who fixed a badly placed label or title in the spec and ran `/ct-groom` again saw no signal at all that nothing had changed.

Now, for each slice whose issue already exists, `/ct-groom` compares:

- **the title** (`#N <Slice>`);
- **the link to the spec** (the `> Slice #N of the epic. Spec: […]` line) — it is spec content, unlike the `ct-order` marker (bookkeeping of ours, outside every comparison). It is compared **whole**. Before, it was compared only by its anchor, because the line was composed with the path exactly as you typed it when invoking the command, and two invocation habits for the same file would have "corrected" each other forever under `--reconcile`; that cause no longer exists (see "The link to the spec" further down), and comparing the whole line detects in addition that the spec has moved file or points at another repo. Immediate consequence on updating: the issues created with the previous version carry a broken relative link, so they **will come out reported as a divergence** — that is correct, that link never worked;
- **the milestone NOT**, since F23: a paired issue always has the run's milestone (see "The scope of a groom is its epic, not the repo"), so that divergence is unreachable from here and you will never see it reported;
- **labels, but only the prefixes whose column the §9 table carries**: `type:` (if there is a `Tipo` column), `area:` (if there is an `Área` column), `touches:` (if there is a `Toca` column), `gate:` (if there is a `Gate` column **or** a `Tipo` column — the gates can come from either of the two). Without the corresponding column, the spec has NO opinion at all about that prefix. `status:` stays **out of the comparison completely, always** — a human or `/ct-next` move it afterwards (`backlog` → `ready` → `in-progress` → `in-review`…) as a normal part of the flow;
- **dependencies** (`## Dependencias`, the `merge-after #N` lines) and **acceptance criteria** (`## Acceptance criteria`) — data the dispatcher genuinely obeys (`merge-after` gates whether a slice can be dispatched; the ACs are injected literally into the agent's prompt). Comparison by set, **only inside the recognized section** (see "Known limits"): a `merge-after #N` (or an AC) written in ANOTHER part of the body — Descripción, a new section added by hand — does not count as a real divergence, but it **is warned about as a note** (since the dispatch hardening, `/ct-next` does not obey it either — before that the dispatcher DID, even though `/ct-groom` could not touch it safely; see "Known limits");
- **Descripción and Protegido** are also compared, but only with a **yes/no**, as a **note, not as a divergence** — they do not count towards the exit code: they are prose that gets edited routinely, and anchoring the exit code to that would leave it at "there is something to review" forever;
- **`## Señal de observabilidad`** is compared only with a **yes/no**, as a **note** (the same treatment as Descripción/Protegido: it does not count towards the exit code, and `--reconcile` does not rewrite it — the signal the slice judge obeys is the one the issue had at dispatch time, just like the gates);
- **`## E2E`** (the end-to-end journeys) is compared and **is rewritten** from the spec, and it **does count towards the `3`**: out of that section come the journeys `/ct-next` seeds into the worktree and the ones `dispatch-check --release` demands to have been traversed, so an issue without it (or with something else) is a slice that does not traverse what the spec asks for. It is the only prose section that is rewritten without excuse: the journey cannot be editable outside the spec's freeze. The case this fixes is the adoption one — an already groomed epic, plus the new `E2E` column, plus `--reconcile`: before, it added the `gate:e2e` label and not the section, leaving the feature inert with the issue saying two different things;
- **`## Contexto del epic`** is compared and **is rewritten** from the spec. It is reported as `note:` and **never** counts towards the `3` — the same treatment as Descripción/Protegido, although unlike them it is rewritten (see "`--reconcile` applies", further down: the distinction is not whose the text is, but a human's right to edit it after creating the issue). `## Contexto heredado` stays out of the comparison **completely, always**: the spec does not own it, and the plugin has no opinion at all about its content.

A known heading is recognized by **exact equality** (not by prefix) — except `## Acceptance criteria`, which tolerates exactly **two** literal forms (`## Acceptance criteria` and `## Acceptance criteria (EARS, 1:1 con tests)`, the two strings `buildIssueBody` has emitted over the project's history). It is a CLOSED set of two elements, not an open prefix: a `## Acceptance criteria propuestos por QA (borrador)` written by a human above the real section is NEVER confused with it (it used to be, with an open prefix — the dispatcher would have injected zero real criteria). Just as exact, a `## Dependencias externas (notas del equipo)` is NEVER confused with the real dependencies section.

The end of a section (where its content finishes) is precise too: any **real ATX heading** (`#` through `######`, indented up to 3 spaces, followed by a space/tab or end of line — not just a literal `## `) ends it, and the interior of a **multi-line HTML comment** (`<!-- … -->` that opens and closes on different lines) is completely invisible to the scanner while it is open — a "commented out" heading in there (some old deps postponed "while it is being decided", say) is never confused with the real section, and the comment survives intact (with its closing `-->`) if `--reconcile` touches the section containing it.

By default, `/ct-groom` **detects and reports, it never changes anything** — each real difference comes out through stderr as `drift: …`; the informative stuff (prose, cosmetically duplicated sections, references outside a section) comes out as `note: …`. Total silence means spec and issue agree on everything the spec can have an opinion about. A **closed issue** is not reported for that alone; if it also diverges in something, a note is added warning that it is closed before applying anything.

A known section **duplicated** in the body (copy-paste, a badly resolved merge) is always warned about — but with an important distinction: duplicating `## Dependencias` or `## Acceptance criteria` **DOES count towards the exit code** (`drift:`), although the mechanism by which each one matters is different:
- **Dependencias** and **Acceptance criteria** behave the same since the dispatch hardening: the dispatcher is section-scoped in both and always reads the **first** occurrence — the second copy is discarded silently. There is no union, but silently discarding a real human edit (which perhaps landed in the second copy after a badly resolved merge) is just as serious: the agent goes on working with criteria/deps a human already corrected, with nothing warning about it. (Before the dispatch hardening, Dependencias was different: the dispatcher read `merge-after #N` scanning the WHOLE body, with no notion of a section, and two copies with different content genuinely got merged — that asymmetry with AC no longer exists.)

Duplicating `## Descripción`/`## Out of scope / Protected` is still merely cosmetic (`note:`, it does not count) — the dispatcher reads neither of the two.

**An existing issue whose slice is NO longer in the §9 table** (the row was deleted, but nobody closed/renumbered the issue) is reported as an **orphan** — before, it was not mentioned at all.

**`--reconcile` is EXPERIMENTAL.** Five rounds of review, each one finding a new way of corrupting a real body (code fences with the wrong closing character/length, multi-line HTML comments, headings that are not a literal `## `, duplicated sections that cannot be resolved on their own), are evidence that this feature's **detection** half (everything above, without `--reconcile` — it never writes anything, safe by construction) is better understood than its **application** half (which does write into the user's real data). As soon as the flag is present — with or without `--dry-run`, before any validation or mutation — `/ct-groom` prints through stderr an explicit warning that it is experimental, that it has corrupted bodies in tests in several ways since fixed, and that it is worth reviewing the issue's diff in GitHub after every run. Without `--reconcile`, none of this changes: zero new warnings, the same behaviour as always.

**`--reconcile`** (opt-in, never by default — an issue may have been edited on purpose, carry discussion, or be closed) applies:

- **title and labels** with a single `gh issue edit --title … --add-label … --remove-label …`; the **link to the spec** travels in the SAME call, inside `--body` (a single-line splice), whenever the line differs in anything. (`--milestone` is never emitted from `/ct-groom` any more: the divergence that activated it is unreachable since F23 — see above.);
- **dependencies and acceptance criteria**, in the SAME call, via `--body`: ONLY the exact range of those two sections inside the existing body is replaced (or inserted/withdrawn, if the whole `## Dependencias` section appears or disappears) — the whole body is never rebuilt. If the AC heading is not found (renamed or deleted by hand), or if Dependencias needs creating but there is no safe anchor to insert it at (typically, `## Out of scope / Protected` cannot be located either — e.g. because of an unclosed code fence ahead of it), `--reconcile` **neither invents where to write nor adds anything blindly** — it gives up cleanly, warns precisely (it never says "just prose" when it is in fact AC/deps left unapplied) and that divergence goes on counting towards the exit code. (Before this, the branch with no safe anchor inserted a new section on every run with no limit at all — verified that it grew 2, 3, 4 times over successive passes.)
- **`## E2E`**, also via `--body` and with the same three-state mechanics as `## Dependencias`: it is rewritten if it differs, inserted whole (right before `## Out of scope / Protected`, its position in the body) if the issue does not have it and the spec now asks for journeys, and withdrawn whole if the spec's cell turned to `no`. It gives up for the same causes as `## Dependencias` —duplicated section or anchor, absent anchor, the only copy inside `## Contexto heredado`— and that giving up **counts towards the `3`**, with the exact reason through `stderr`;
- **`## Contexto del epic`**, also via `--body` (a surgical section splice, just like AC/Dependencias): if the spec carries text and the section does not yet exist in the issue (one from before this round), it is inserted whole right **before `## Contexto heredado`** (without touching a byte of its content) or, if that section is not there, right before `## Acceptance criteria` — the order the contract fixes is epic → heredado → criteria. With neither of the two headings, no position is invented: nothing is written and it is said through `note:` (it never counts towards the `3`). If the spec stops carrying the section (or carries it empty), it is withdrawn whole; if it carries it but malformed, nothing is touched (see above). "Whose the text is" is not what distinguishes this section from Descripción/Protegido (the spec owns all three) — what distinguishes it is that editing it by hand in a single issue is exactly the divergence that keeping it up to date exists to eliminate.
- **Descripción, Protegido, the inherited context, duplicated sections and references outside a section are NEVER applied**, not even with `--reconcile` — Descripción/Protegido are prose of arbitrary length that a human legitimately edits in their issue (a splice cannot guarantee that elaboration is not lost), the inherited context is not text the spec owns at all, and the duplicated/outside-a-section ones live in a place of the body that `--reconcile` cannot touch safely.
- **Orphan issues are NEVER touched** — there is no slice in the §9 table to reconcile them against.

A `gh` failure aborts with a clear message (the same convention as the rest of the file: it never carries on blindly with the remaining slices). Editing a closed issue does not reopen it, so `--reconcile` updates it all the same.

All of this works under **`--dry-run`** too (with `--repo`; without it there is nothing to compare against) — with one important caveat: **`--dry-run --repo` is no longer offline**. Before F5, `--dry-run` never touched `gh`; now, with `--repo`, it makes a real read (listing the repo's issues) in order to compare — it needs network and valid `gh` authentication against that repo, just like the real run. Without `--repo`, it is still pure (it only prints the plan). Under `--dry-run --repo` you get the same report as the real run, and with `--reconcile` it also announces what it would apply (by category — title/link-to-the-spec/labels/dependencies/AC/epic context — without dumping the whole rebuilt `--body`) — but it never mutates anything.

**Exit code**: `0` if there is no real divergence (or if `--reconcile` resolved it entirely), **`1`** if the run stopped dead —the two gates of "The scope of a groom is its epic" (which fall before any mutation and say so: `no se ha creado ni modificado nada`), a `gh` read failure, a write failure halfway, or something about `--project` that could not be taken as good: an unmet precondition (the project has no `Sprint` iteration field, or no iteration covers today) or one of its bounded reads that could not be ruled out as incomplete (the project's fields, its item list)—, `2` if the §9 table is invalid (as always) or if the spec does not pass the freeze gate (a pending `[NEEDS CLARIFICATION`, `## Hipótesis` absent or empty — see above), and **`3`** if something real is left unreconciled — a divergence of title/link/labels/AC/deps/`## E2E`, a duplicated `## Dependencias`/`## Acceptance criteria` section, a `--reconcile` gap (AC/deps with no locatable section, or a duplicated section that `--reconcile` cannot resolve on its own — there is no code that decides which copy is the right one), or an orphan issue. `3` is deliberately different from `0` and from `2` — a non-zero exit here would be as bad as the silence this corrects, but in the opposite direction. Descripción/Protegido, their duplicates, and the references outside a section **never** count towards the `3` — they are informative notes.

`--dry-run` and the real run without `--reconcile` give the **same `3`** for the same divergence, by parity (same condition, same signal). Watch out if you automate this: with `groom --dry-run && groom`, a `3` in the `--dry-run` **cuts the chain** exactly when there is something `--reconcile` could apply — if you want "review, and if there is something to fix, apply it", check the exit code explicitly instead of relying on `&&`.

### The link to the spec

The first line of every issue's body is its only traceability back to the section that originated it:

```
> Slice `#1` of the epic. Spec: [docs/specs/plan-design.md § 9. Slices](https://github.com/owner/repo/blob/main/docs/specs/plan-design.md#9-slices)
```

Until the previous version that line was `[docs/specs/plan-design.md#9](docs/specs/plan-design.md#9)`, and it was broken twice over (checked against GitHub, not deduced):

- **the relative path does not resolve from an issue.** GitHub returns the href as it is; at `github.com/owner/repo/issues/N` that resolves against that URL and gives a 404. In a file of the repo it would work; in an issue, which is where the line lives, it does not.
- **the anchor did not exist.** The section number (`#9`) was emitted, but the anchor GitHub generates for `## 9. Slices` is `#9-slices`. Even if the link had resolved, it would have landed at the top of the document.

Now:

- **the URL is absolute and points at the default branch of the repo where the spec lives** (not at a sha). The spec is a living document and `/ct-groom` treats it as such — divergence detection compares each issue against TODAY's §9; a permalink to a sha would freeze the link at a version that may have stopped being the one the tool compares against. Neither is the branch you invoke from used: that is not a property of the repository but of whoever invokes (and a feature branch is deleted on merging).
- **the anchor comes from the text of the real heading** the table lives under, with the same rules by which GitHub generates anchors (lowercase, spaces to hyphens, punctuation dropped, a `-1`/`-2` suffix when the same text repeats in the document). The heading does not have to be called "9" nor be the ninth one: the table is located, as always, by its column header.
- **it is verified before being written.** `/ct-groom` asks GitHub for the file rendered on that branch and checks that the anchor is genuinely in it. An absolute link to something unpublished is the same defect with a different face.

When the verification does not pass, **no half-link is written**: the line stays as a text reference, with the reason inside it, and it warns through stderr:

```
> Slice `#1` of the epic. Spec: `docs/specs/plan-design.md` § `9. Slices` — sin enlace: the spec is not published on the default branch of the repository (owner/repo, branch main)
```

The possible reasons: the spec is not in a git repo, it falls outside the repo's tree, the repo has no `origin` remote, the remote is not a recognizable URL, the default branch could not be resolved, or **the spec is not pushed yet** (by far the most common one: you write it, you groom, and you push afterwards). Intermediate case: if the file is published but the anchor does not appear in the published copy (a spec edited locally and not pushed), the **file** is linked —which does work— with no fragment, and it warns.

**Groom after pushing the spec.** Idempotence is only by existence: if a real run creates the issues with the degraded reference, the next run reports the divergence but does not apply it without `--reconcile` (EXPERIMENTAL). A `--dry-run` before the real run shows exactly the same line and the same warnings.

#### `--section` is obsolete

`--section N` is still accepted (it breaks no existing invocation) but **it is ignored, and you are warned that it is ignored**. It never decided what got groomed —the table has always been located by its `Slice` + `Dep` column header—; the only thing it did was compose the link's `#N` anchor, which is precisely the anchor that does not exist. Take it out of your invocations.

#### Known limits

- A `merge-after #N` (or an AC) written **outside** its recognized section is warned about as a note, but `--reconcile` never touches it — the domain of detection-that-counts-towards-the-exit-code and that of application are, deliberately, the same one (only the recognized section): scanning the whole body in order to APPLY would risk the kind of human-content corruption this design avoids elsewhere.
- The link points at the default branch: if the spec's file is **moved or renamed** afterwards, the link of the already created issues dies. `/ct-groom` does **detect** it on the next run (it compares the whole line), but it does not correct it without `--reconcile`.
- The link verification adds **two reads** to `gh` (`repo view` and `api …/contents`) on every run, including those of `--dry-run` without `--repo` — which is why those are no longer 100% offline. If `gh` cannot answer, the link degrades with a warning instead of aborting the groom.
- A known section **duplicated**: only the first occurrence is compared, and **none is rewritten** while there are two — `--reconcile` does not decide which copy is the plugin's (one may be text pasted inside `## Contexto heredado`), so it gives up and says so. Both copies survive intact (it warns, it does not correct on its own — and for AC/Dependencias, it counts towards the exit code, see above).
