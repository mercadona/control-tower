# `/ct-next` — reference and design

> Text moved whole from `plugin/commands/ct-next.md` (sub-issue #93). The command keeps the invocation, the exit-code table and a link to this document; what follows is the reference for each mechanism and the history of the decisions (rounds F11…F38) that left it this way. Where the text says «this document» or «below», it means this file.

The invocation:

```
node ${CLAUDE_PLUGIN_ROOT}/scripts/ct-next.mjs --repo "<owner/repo>" --cap 1 --dry-run   # dry first
node ${CLAUDE_PLUGIN_ROOT}/scripts/ct-next.mjs --repo "<owner/repo>" --cap 1             # and for real
```

Each slice runs in its own worktree `.worktrees/<n>`, with its account (account map) and its `.agent/SLICE.md` seeded (F22 — it used to be `.agent/STATE.md`, see below); `cmux` starts `claude`, which hydrates itself (Phase 1's SessionStart hook).

It only dispatches issues in `status:ready` — `/ct-groom` creates them in `status:backlog`, so a human has to promote them first. If there is nothing to launch, check that the epic has issues in `status:ready`.

**Dependency order, per epic (D1):** the `<!-- ct-order:N -->` that `/ct-groom` writes numbers slices 1..N PER EPIC (one invocation of `/ct-groom` = one `--milestone` = one epic), not per repo — so two epics of the same repo legitimately reuse the same order numbers. `/ct-next` translates each `merge-after #N` against the ISSUE'S OWN real milestone, never against the whole repo. If two different issues share milestone+order (an accidental re-groom, or two epics that fell into the same milestone because `--milestone` was not passed — the default value is the literal `"Epic"`), that epic is **excluded from the batch** (it is neither dispatched nor counted against the cap) until it is fixed in GitHub — `/ct-next` warns why (`aviso: colisión de orden…`) and carries on dispatching the rest of the epics as normal, which are unaffected. Moving an issue to another milestone by hand, after grooming it, can silently re-point its dependencies at another epic — avoid doing it unless you know what it implies.

**Dependencies are only read inside "## Dependencias" (D1):** a `merge-after #N` written outside that section (in the prose of an AC, under "## Descripción", etc.) no longer gates the dispatch — same scope as `/ct-groom --reconcile`. `/ct-next` warns (`aviso: #N tiene "merge-after #M" fuera de la sección…`) when it detects one, but dispatches anyway: the warning is only so that you fix the text if you really did intend that dependency.

The three warnings above (order collision, `status:` ambiguity, dependency outside the section) are printed ALWAYS, BEFORE anything is selected — they never block on their own (except the exclusion of the collided epic, which is already applied surgically before this point): they are data diagnostics, not part of the dispatch plan.

**Output channel (F16).** The plugin's three executables use the same criterion: **stdout is the product** (the dispatch plan, the selection, the reason for blocking, the record of what was launched — what makes sense to redirect or parse) and **stderr is the diagnostics** (`aviso:`, `recordatorio:`, `ATENCIÓN:`, and every abort). Until F16, `/ct-next` emitted its warnings on **stdout** while `/ct-groom` and `/ct-init` emitted them on stderr: a real run of `/ct-next` with warnings on screen left **0 bytes on stderr**, so `ct-next --dry-run > plan.txt` carried the diagnostics inside the plan and whoever captured stderr expecting the warnings got nothing. If you redirect the two channels to different places, bear in mind that cross-references of the kind «see the warning» now point at the other file.

**A slice's state is not product (F22).** A slice's worktree has **two** state files and only one of them talks about that work:

| File | What it is | git |
|---|---|---|
| `.agent/STATE.md` | the coordinator session's own, exactly as it came in the base | tracked, **at zero diff**: the dispatcher does not touch it |
| `.agent/SLICE.md` | the slice's state | **ignored**, never committable |

Every reader of the state —the plugin's two hooks that read `.agent/` (F27 added a third, `PreToolUse`, which does not) and `/ct-next` itself— applies the same rule: **if `.agent/SLICE.md` exists, that is the state; if not, `.agent/STATE.md`**. The file's presence is the signal for «I am in a slice worktree»; there is no environment variable and no path detection. And the kickoff that `/ct-next` seeds names only `.agent/SLICE.md` to the dispatched agent — `.agent/STATE.md` does not appear in the kickoff (`scripts/kickoff.js:167`, `:190`, `:226`). Before this round it did: the kickoff told it «hydrate from `.agent/STATE.md`» and asked it to update the file when finished, so the plugin's own prompt was asking the agent, turn after turn, to edit the coordinator's tracked file — exactly the contamination this round came to eliminate.

**Every message names the file it actually read, not a constant (F22).** `resolveStatePath(cwd)` (`scripts/state-paths.js`) returns `{ path, kind, rel }` — `rel` is the relative path (`.agent/SLICE.md` or `.agent/STATE.md`) that was actually resolved for that `cwd`, and it travels as the `stateRel` option (with the coordinator as the default value) all the way to `readBlocked`, `blockNotice`, `unreadableNotice`, `composeHydration` and `classifyStopState`. Without this, any warning composed inside a slice's worktree —the blocking one, the unreadable-frontmatter one, the «you have fallen behind» one from the `Stop` hook— would cite `.agent/STATE.md` even though the file that was actually read (and the one that has to be fixed) was `.agent/SLICE.md`: a message that sends its reader off to edit the wrong file.

To guarantee the «ignored», `/ct-next` writes the rule into the `info/exclude` of git's **common directory** on every dispatch (one write covers the coordinator and every worktree, and is never committed), and afterwards **verifies the effect**: if `git status --porcelain` still sees the file, the dispatch is aborted and the claim is reverted. `/ct-init` additionally leaves the line in the repo's `.gitignore`, which is the committed and shared route.

And `dispatch-check --release` **refuses with exit 5** in three cases, not just one: if the branch introduces `.agent/STATE.md` or `.agent/SLICE.md` (with the exact command to restore it); if the comparison base cannot be determined at all (no `base:` in the seed, no `origin/HEAD`, no `main`, no `master` — what could not be compared is not asserted "clean"); and if the resolved base turns out to be the SAME commit as HEAD, because a diff against itself comes out empty by construction and `SLICE.md` is agent-reachable: an agent (deliberately or through a bug) that rewrote its own `base:` to the commit where it had already committed the contamination would neutralise the gate if an empty diff counted as "clean". And the comparison runs with `--no-relative --no-renames`: without that, a `diff.relative=true` in the caller's config (combined with a cwd in a subdirectory) or `git diff`'s default rename heuristic could leave the contaminating file outside what the gate looks at, with nobody having asked for it. It is a gate, not a warning: a check that only prints is not a check.

**The `e2e` field of `.agent/SLICE.md`** is seeded by `/ct-next` just like `gates`: by reading the `## E2E` section of the **issue** itself (never the spec, which the dispatcher does not open) with `extractE2eRuns` — the same function, not a second reading, that `dispatch-check --release` uses to compare (see just below). It is a LIST of verbatim journeys, never a sentence; with no section in the issue, the seeded list is empty, and empty means "this slice has nothing to traverse", not a field that is missing.

With journeys declared, `dispatch-check --release` adds a fourth gate, distinct from the three of exit 5 and from the one of exit 7 (which requires a **delivered** run, `closed: "delivered"` in `.agent/run-<issue>.json` — see the full reference): **exit 8**, the correspondence between what the run says it traversed and what the issue asks for. It crosses `e2eRuns` from `.agent/run-<issue>.json` —what `ct-step`'s machine recorded in the worktree as it went, and which for that very reason is agent-reachable, the same caution that already justifies exit 5— against the `## E2E` section of the **issue**, which the agent does not control. If the run does not cover some journey the issue declares, `--release` refuses naming which ones, without touching any label; if the issue's body cannot be read, it is not asserted that there are no journeys either — only that it could not be checked, and it does not release; and if the section is absent but the `gate:e2e` label is still on (issue edited by hand after the groom), it releases anyway but warns on stderr about the discrepancy. (Since F38 there is one more gate, the last one: **exit 9**, the go of the `plan` gate — see «The guardrail on the go» below.)

**A worktree seeded by a version older than F22** has no `SLICE.md`. `/ct-next` does not read its `.agent/STATE.md` to detect blocks —in a new worktree that file is the coordinator's and its `blocked` does not talk about the slice—: it warns that it has not checked and asks you to look by hand. Nothing is migrated: mutating a live agent's tree is worse than the problem. And the warning **does not pick a cause**: the absence of `SLICE.md` has two, indistinguishable from the dispatcher — the old scheme, or a file that was seeded and then deleted. The second is new to this round and could not happen to the tracked `STATE.md`: `.agent/SLICE.md` is ignored, so a `git clean -x` in the worktree takes it away.

**`dist/` is what gets EXECUTED, not `hooks/` (F22).** `hooks/hooks.json` starts `dist/session-start.js`, `dist/stop.js` and `dist/commit-keyword-guard.js` —the bundles `npm run build` generates— and not the sources in `hooks/`. `dist/` is TRACKED: **every change to `hooks/`, or to any module of `scripts/` that those hooks import, has to carry a rebuilt `dist/` in the same commit**, or the repo keeps shipping the old hook while the source already says something else. It happened for real during this very round: a commit changed `hooks/session-start.js` and `hooks/stop.js` to read by the SLICE.md/STATE.md precedence above and did not touch `dist/`, so the branch kept shipping the hooks WITHOUT that rule — and the suite stayed **green**, because `npm test` runs `npm run build` first: it tests a freshly built `dist/` while the committed one rots without anything noticing. Before any commit that touches `hooks/`: `npm run build`, and look at the diff of `dist/*.js` as part of the change itself — it is not an artefact that "CI will generate anyway".

**Where the boundary falls, and why the REASON FOR BLOCKING is product (F17, written here in F18).** It has been reported two rounds running as if it were an oversight, so let it be said where whoever uses the command reads it: `/ct-next` dispatching nothing **is not a diagnostic about the run, it is its result**. The question the command answers is «what gets dispatched now?», and «nothing, and this is exactly what prevents it, with its remedy» answers it in full. An `aviso:` is the other thing: the run did its job and **on top of that** notes something down. Three reasons why the reason for blocking does not move to stderr:

1. after printing it, `exit 0` happens. On stderr, a real blocked run would leave **empty stdout with exit 0** — which reads as «all good, nothing to report», precisely the false positive this criterion came to fight;
2. `--dry-run` does not change WHAT the product is, only whether the plan gets executed. Routing the same sentence to a different channel depending on a flag would leave different things in `out.txt` without anybody having asked for anything different: **a channel rule that depends on a flag is not a rule**;
3. it is pinned by tests (`f17-issue-closure.test.js`), one about behaviour and another that checks that the criterion written in `ct-next.mjs` still classifies it as stdout — so that code and criterion cannot diverge in silence.

**When several block, they are all said (F16).** A `ready` slice can be held up by more than one issue at a time — several occupants of the global serialising lane (`migration`/`ci`/`pbxproj`), several owners of different tokens, or the same token in the hands of two issues. Before, **one** was named, which invited you to resolve that one, run again and find yourself just as blocked, as many rounds as there were blockers. Now the message says how many there are, enumerates them (capped at the first few, with the total count always visible), separates the remedy by status (`in-review` → merge; `in-progress` → wait, with the stale-claim note if there is no local evidence of life) and makes it explicit that **resolving just one dispatches nothing**. Same criterion in "there is nothing ready": with issues in `status:backlog` the message no longer says «yet» —promoting them is your gate, not an event that arrives on its own— and a repo with no open issue at all is distinguished from a whole epic waiting for promotion.

**Claim and release (W-C):** for each selected slice, `/ct-next` calls `dispatch-check <issue> --repo <repo>` in code (it claims `status:ready` → `status:in-progress`) BEFORE creating the worktree — it is no longer merely an instruction in the kickoff that the agent might not execute. `dispatch-check` has an exit-code contract of its own for the three consequences the caller cares about (finding 4 of the last hardening round — before, all of this shared a single exit 1 that `/ct-next` had to disambiguate by parsing free text; no longer):

- **Exit 1 — collision detected in time, or race lost with a clean revert** (the issue goes back to `status:ready`, nothing mutated and nothing stuck): a NORMAL outcome of the protocol — that slice is skipped (the reason is printed) and the rest of the batch continues if `--cap` allows more.
- **Exit 3 — one-off infrastructure failure** (the candidate's labels could not be read, or the claim never even got written, or the readback failed but the revert DID succeed): nothing was mutated either — it is treated the same as a collision (skip and continue), but the message makes it explicit that this is NOT a normal collision, but a `gh` that failed one time.
- **Exit 4 — orphaned issue** (race lost OR readback failure, and the subsequent revert ALSO failed — the issue really is stuck in `status:in-progress` with nobody working on it): this one DOES stop the whole batch. `dispatch-check` already prints its own `ATENCIÓN` warning with the exact manual command to free it by hand; you have to run it before retrying anything else against that repo.
- If `dispatch-check` terminates from a SIGNAL (e.g. a real Ctrl-C during the claim that also reaches the subprocess) instead of an exit code, `/ct-next` explicitly distinguishes that from "bug or bad configuration" and warns that the claim may have been written before it died, with the manual revert command just in case.

If the claim is obtained but the dispatch fails AFTERWARDS (`git worktree add` itself, the seeding of `.agent/SLICE.md`, or the launch of `cmux`), `/ct-next` reverts the claim to `status:ready` automatically — and if that revert also fails, it says so loudly and prints the exact manual command to fix it. `--dry-run` shows which issue would be claimed, without really running `dispatch-check` (no real `gh` is touched). The **release** (`status:in-progress` → `status:in-review`) still lives in the kickoff — the launched agent's own prompt already carries the literal command `dispatch-check <issue> --repo <repo> --release` for when it finishes and the PR is open; Phase 3's PR-conformance gate is the backstop if the agent does not run it.

**What the release drops and what it does NOT drop (F13).** `--release` frees the **cap** (it stops counting as a live agent) but **not** the `area:`/`touches:` tokens: a `status:in-review` retains them until its issue is closed on merge. They are two resources with two criteria, not one:

| | `status:in-progress` | `status:in-review` |
|---|---|---|
| Occupies `--cap` | yes (there is an agent running) | **no** |
| Retains `area:`/`touches:` | yes | **yes, until the merge** |
| Satisfies a `merge-after` | no | no (it has to close as *completed*) |
| Stale-claim detection | yes (crossed with worktree/branch/cmux session) | **no** — having no session there is the normal thing |

Before, `--release` dropped both things at once: between the PR opening and its merge, the next slice of the same area saw the ground clear and branched off a base that did not yet contain that work. The lock's window was shorter than the conflict's window. Practical consequence: **an unmerged PR holds up its area neighbours**, and `/ct-next` says so by that name (`status:in-review`, not "wait for it to finish") instead of sending you off to wait for an agent that does not exist.

**Sending a slice rejected in review back to the workbench (F13, corrected in F15):**
```
node ${CLAUDE_PLUGIN_ROOT}/scripts/dispatch-check.mjs <issue> --repo "<owner/repo>" --reopen
```
`status:in-review` was a **terminal** state: there was no transition back except the protocol's failure reverts, so rejecting a PR at the gate took that slice out of the loop forever, and with it everything that depended on it. `--reopen` is that edge, and it is deliberately manual: it **reads** the issue's real state and **requires** `status:in-review` (exit 2 if not, without touching any label — a `gh issue edit` by hand checks nothing and can leave two `status:` at once). Nothing automatic ever invokes it: not `/ct-next`, not the kickoff.

**F15 — `--reopen` leaves the slice in `status:in-progress`, not in `status:ready`.** The first version sent it to `ready`, and `ready` **does not retain tokens**: while someone was fixing on top of a rejected PR, a neighbour sharing `area:`/`touches:` could be dispatched over a `main` that did not contain that work — exactly the window F13 came to close, reopened by its own return edge. Reproduced by construction with `planDispatch`: with the issue in `in-review`, the neighbour in the same area is skipped; with that same issue in `ready`, `runningTouches` comes out empty. The root is that `ready` meant two incompatible things — "it was never started" and "it was rejected and there is unmerged work on top that is being worked on". `in-progress` describes the second one exactly in both ledgers: it retains tokens (its work is still unmerged) **and** occupies cap (this time there really is somebody redoing it), and the worktree and the branch are still on disk, so it does not fire the false alarm of an orphaned claim either. A consequence to keep in mind: **reopening does not unblock the neighbours**; the only thing that unblocks them is the merge.

`--reopen` deletes nothing from disk: it prints what is left of the previous round (worktree `.worktrees/<n>`, branch `feat/<n>`) and the two possible paths — fix on top of what is already there (the normal thing after a rejection; in that case do **not** invoke `/ct-next`, which would refuse because the worktree/branch are occupied) or delete and start again, with the exact commands.

**Abandoning a slice and sending it back to the queue (F15):**
```
node ${CLAUDE_PLUGIN_ROOT}/scripts/dispatch-check.mjs <issue> --repo "<owner/repo>" --requeue
```
The other half of the return edge: `in-progress` → `ready`, for the "I start from scratch" path and for **breaking a dead claim** (the checked version of the `gh issue edit --add-label status:ready --remove-label status:in-progress` you used to have to do by hand). It is the only transition that drops tokens without a merge, so it **checks before declaring**: it requires exactly `status:in-progress`, and it requires that on this machine neither `.worktrees/<n>` nor `feat/<n>` is left — if they are, it refuses and gives the deletion commands, because sending it back to `ready` with its work alive would reopen the same window. If it **could not look** (git does not answer from there) it also refuses: what has not been seen is not declared absent. And what it cannot check it says every time, instead of leaving it implicit: the branch on the remote and the open PR are outside its reach; if they are still there, that work is still unmerged and nobody is retaining its area any more.

**Dead claims that hog the cap (F13).** Stale-claim detection (worktree / branch `feat/<n>` / `cmux` session, all local to this machine) is no longer consulted only when explaining a collision: also when the cap is full. An abandoned `status:in-progress` that shares **no** token with the candidate but does occupy the only cap slot produced "raise `--cap`, or wait for one to finish" — sending you off to wait for an agent that no longer exists. The usual limit still stands: **nothing watches the claims between invocations** (the claim is a label, with no heartbeat), so only whoever is running `/ct-next` at that moment finds out; and the evidence is local, so "abandoned" is never asserted, only "there is no trace of it here".

**A dependency that is never going to be satisfied (F13).** A `merge-after` counts as satisfied only if its issue is **closed as *completed***. Closing a discarded slice as *not planned* — the semantically correct thing — leaves all its dependants waiting forever, and the message said "#7 needs merging" just as if the work were still under way. Now the real closure status is named, along with the remedy (drop the dep, or reopen and close as *completed* if the work really was done). The opposite trap —an issue closed as *completed* without anything having been merged satisfies the dep just the same— **is no longer dismissed as "that requires bad intent"**: see the next section, which corrects that assertion with evidence.

**F18 — the premise that "that only happens if somebody does something wrong on purpose" was false, and the check did not cost what was claimed.** Both terms used to justify not looking at who closed an issue were wrong:

- **no intent is needed at all.** GitHub applies the *closing keywords* of **any commit message** that reaches the default branch, and **quotes do not protect you**: in a production repo, a **documentation** commit whose body contained the string `Closes #451` —inside a sentence that explained precisely that the kickoff did *not* carry it— closed issue #451 as *completed*. Nobody meant to close anything, and a slice with a `merge-after` on it had its dependency «satisfied» over non-existent work;
- **it does not cost one call per issue.** A single GraphQL query with aliases resolves N issues at once: measured, **97 closed issues in one call, 2.8 s**.

What `/ct-next` does with that, and what it does **not**: it asks —in **one** call per run, and only if there is something to ask about— about the dependencies that ALREADY count as satisfied, and it **warns** (it never blocks) when one of them is recorded as closed by a **loose commit that belongs to no merged PR**. What it does **not** do is require the closure to come from a PR: in that very repo, **86 of 97** issues closed as *completed* have no closer at all — a person closed them by hand, which is the majority practice **and a step prescribed by this very document** when you dispatch with `--base <another-branch>`. A gate over "closed by a merged PR" would have left 86 dependencies unsatisfied in one go. That is why it is a detector and not a lock; if the query fails, it says so and the dispatch carries on.

**F18 — "PR merged, issue open" stops being a dilemma.** The blocking messages used to say «merge its PR — or, if it was merged already and the issue is still open, close it», and working out which of the two was true fell to the human. A slice's branch is deterministic (`feat/<n>`), so in the **same** query as the previous section (marginal network cost of zero) it asks whether a **merged** PR with that head exists: when there is one, the warning says which and since when, with the exact `gh issue close <n> --reason completed`. It only goes in that direction: its NOT showing up proves nothing (the work may have gone out on a branch with another name), and that is why the silence is not reported as «it was not merged».

**F18 — a CLOSED issue that kept its `status:` label used to vanish from the dispatcher without a word.** `/ct-next` only sweeps **open** issues: a closed one with `status:ready` still on stops existing for it, is named nowhere, and the next run falls to the repo's next `status:ready` and explains in detail why *that* one is not dispatchable. In the field, the operator read a careful explanation of something irrelevant and got no hint that their work had fallen out of the queue. Now **a single aggregated warning** comes out (not one per issue: the measured rate is **10 out of 99** closed, because closing the issue and taking the label off are two separate acts and nothing checks the second) that groups the numbers by status, starting with the `status:ready` ones — the ones that were in the queue. `status:in-review` does **not** count as an anomaly: closing from there is the normal end of a slice and nothing takes that label off; its count is stated too, so that the total does not hide part of what was seen.

**F18 — an agent that declares itself BLOCKED used to leave its claim on forever.** The kickoff asks it to mark `blocked: {reason, unblock}` in its worktree's state file and STOP; the issue stays in `status:in-progress` retaining tokens and one `--cap` slot, and **no transition of the loop gets it out of there**: stale-claim detection does not see it (the worktree and the branch DO exist), `--requeue` refuses for exactly that reason, and `--release` would be lying (there is no PR). The dispatcher now **reads** that file (a local read, no network, on the path it already walks — since F22, `.agent/SLICE.md`; before F22 it was `.agent/STATE.md`, see the section above) and warns with the reason and the unblock the agent itself wrote down. There is no automatic fix: it is a human decision, and it is said as such.

**F19 — the dispatcher reported success over an agent that NEVER started.** First real dispatch against production: exit 0, `lanzados 1/1`, «verified: the cmux session is running in that directory». What was in that terminal was `[oh-my-zsh] Would you like to update? [Y/n] laude --dangerously-skip-…` followed by `zsh: command not found: laude` — the one-character `read` of oh-my-zsh's prompt ate the `c` while cmux was typing the command. Result: twenty minutes in `status:in-progress` **claimed by nobody**, retaining `area:plan` and the whole repo's `pbxproj` serialising lane; zero commits, zero PRs. The root: the **container** was being checked (a cmux window exists with the requested title and cwd) instead of the **content** (the command actually got executed) — and that window is opened by the dispatcher itself, just as the "modified" `.agent/STATE.md` that also fooled the humans was its own seed.

Two changes. **(a)** cmux's `--command` does not execute: it *types* (its own help, embedded in the binary: «Send text+Enter to the new workspace after creation»). Several KB with the kickoff inside are no longer typed, but **one short line** that does a `.` over a script `/ct-next` writes to disk; the kickoff travels by file, where no prompt can bite it. It is still sourced in the user's login shell, and not in a shell with no rc, **on purpose**: `claude` may be an alias or a function defined in that rc. **(b)** That script writes a **sentinel** before launching the agent — a file that can only exist if the command ran — with the shell's real `$PWD` and whether `claude` resolves *in that shell* (something `/ct-next`'s preflight, which only sees its own PATH, could never know). `/ct-next` waits for that sentinel up to `CT_NEXT_LAUNCH_TIMEOUT_MS` (F20 raised it to 15000 by default, see below; on the happy path it returns as soon as it appears, it does not wait out the cap).

**F20 — there is no exec route in cmux at all, so the typing is REPEATED.** F19 left `--layout` noted down as a possible exec without being able to test it. Measured now against the installed cmux, launching and closing test workspaces: `--layout` with a `command` surface **also types** (the text comes out echoed behind the session's prompt, and the process hangs off a login `-/bin/zsh`), and on top of that it **ignores the `--cwd`** you pass it. `new-surface` does not accept any `--command`; the only type that starts a binary on its own (`agent-session --provider claude`) is cmux's own Claude session, with no way of passing it arguments or a prompt. And `--env` does reach the shell, but `ZDOTDIR` does not (cmux/Ghostty uses it for its integration and it arrives empty), so you cannot inject an rc that starts the agent by itself either.

What was measured, and what dismantles the 8000 ms: **a clean login shell executes what was typed at ~723 ms**, and **6 out of 6 consecutive launches with F19's mechanism gave ZERO sentinels** — the screen showed `[oh-my-zsh] Would you like to update? [Y/n]` and, below it, `zsh: permission denied: /…/launch.sh` (the `.` had been eaten by the `read`). Waiting longer was never going to fix it. So `CT_NEXT_LAUNCH_TIMEOUT_MS` goes from being "the only thing that is done" to being the **total budget** (and it rises from 8000 to **15000**, for the opposite reason to the one F19 rejected: with a single wait, more time bought nothing; with resends, every extra 2500 ms is **one more attempt**), split into attempts of 2500 ms: if the sentinel is not there, `/ct-next` **resends the same line** to that same session (`cmux send` + `send-key Enter`) and waits again. With resending: **5 out of 5** started, all on the second attempt, at ~2.9 s and with **a single** agent each (validated end-to-end with the code that is shipped: launcher with a guard, `send` + `send-key`). With the machine loaded, that same measurement needed **two** resends, ~6.8–7.0 s, and 1 in 3 went past the old 8000 — hence the 15000. Resending is safe because the launcher carries an **idempotency guard** — if its sentinel already exists, that sourcing relaunches nothing — so two lines that both arrive still produce **a single** agent. When there were resends it is said in the output even though the dispatch went fine: a shell that eats what is typed at it is a fact you need to find out about. And if not even the resends are enough, the message distinguishes «it was resent N times and still did not execute» from «there was no budget left to resend» and from «the resend could not be addressed» — three situations that lead you to look in different places.

The verdicts: sentinel with the correct `$PWD` and `claude` resolvable → **launched**. `claude` does not resolve → certainty that there will be no agent, so **everything** is undone (worktree, branch and claim) and exit 1. A different `$PWD` → there is a live agent in the wrong place: nothing is deleted, it does not count as launched, exit 1. **Sentinel absent when the cap runs out** → «the command never ran» cannot be told apart from «the shell is still starting», so it is **not** called launched (exit 1) and the claim is **not** reverted either: reverting it with an agent that starts late would destroy live work, whereas the residue declared with its exact commands is recoverable. The rule that remains: *if it cannot be confirmed that the agent started, the result cannot be "launched" with exit 0.*

**F20 — the happy path harvested nothing (`cosecha pendiente`).** Every path in the plugin that deletes a worktree is a **failure** path; none covered **success**. Observed on the first slice that finished well: PR merged, issue closed, and `.worktrees/451` + `feat/451` still on disk — with its `claude` alive for **thirteen hours**, with the work already delivered. With six slices that is six full checkouts, six dead branches and six zombie agents. And there is an edge: `/ct-next` **refuses** to dispatch if `.worktrees/<n>` exists, so the residue of a finished slice blocks any future retry of that same number. Now every run crosses the already-merged issues against `.worktrees/` and `git branch --list 'feat/*'` (two cheap local queries; cmux is only asked if there is already something to count) and emits a `cosecha pendiente:` warning with the list and **the exact commands**. It **deletes nothing**, and that is deliberate: "merged" is not "nobody is touching that" — there may be unpushed changes, and deleting a worktree is irreversible. It is the same criterion by which `--requeue` refuses to act while they exist. What no longer happens is that nobody mentions it. And since 0.52.0 there is a way of harvesting it that does not require typing the `git` commands by hand: `node <plugin>/scripts/dispatch-check.mjs <n> --repo <o/r> --collect` closes the cmux workspace whose directory is that worktree, deletes `.worktrees/<n>` and deletes `feat/<n>` — but **only** if that branch's PR is MERGED, the tree is clean (`git status --porcelain --untracked-files=all` empty) and the branch's local tip is the `headRefOid` that the PR merged. If any of the three fails it touches nothing and says which (exit `10` preserved, `1` wait, `3` could not read, `4` half a harvest with the commands that remain, `0` harvested), and `--dry-run` prints the decision without mutating. It is a **declared divergence** from `docs/superpowers/specs/2026-08-31-fusion-con-app-companion-design.md` §5.5 («harvesting the worktree remains a warning, not an automatic deletion»): the warning is still there, and this command is the door through which a sweep can harvest it without anybody deciding by eye. And with `--bq <proyecto:dataset.tabla>` the harvest first leaves the slice's row in BigQuery: if the load fails, exit `11` (a code of its own: `10` is "the disk disagrees with the PR" and its reader looks at the worktree) and nothing is deleted.

**F20 — who is who (`role`).** There are **two** live sessions per repo with opposite roles: the **coordinator** of the main checkout (it grooms, dispatches, reviews, merges) and the **dispatched** one in each `.worktrees/<n>` (it implements its slice and stops). That split was only written inside the kickoff that one of the two received, so it was lost as soon as that session re-hydrated from its `STATE.md`. Now it is a `role` field in the frontmatter of both files — the one seeded by `/ct-next` and `/ct-init`'s template — for the same reason as `blocked`: what has to survive a re-hydration is a field, not a sentence inside another field. No code decides anything with it.

**F19 — the aggregated warning about labels on closed issues was correct but STATIC.** Those ten cases do not change by themselves, so the paragraph came out identical on every run and got discounted from the third onwards — and then a new one on the list is no longer seen. Two fixes: **(a)** the severity gradient that was flattened — `status:ready` (it fell out of the dispatch queue) and `in-progress` (a claim never dropped) stay in the headline; `status:blocked` is **inert** (it retains no tokens, it blocks nothing) and moves to a separate count, like the `in-review` ones; **(b)** a **per-case acknowledgement** reusing `.agent/conventions-ack.md` (F14's mechanism): a line `residuo-status: 2026-07-28 — #101, #102 <por qué se quedan>` silences **those numbers** and keeps warning about new ones. It accumulates across lines (one decision per date, without having to edit the previous one) and an acknowledgement **with no numbers** silences nothing and says so — there is no wildcard for "all", which would give back the same static silence.

**Exit code of `/ct-next` (real path, without `--dry-run`):** when it finishes processing the batch it always prints `lanzados X/Y slice(s) seleccionados de esta tanda` (X may be less than Y, even 0, without that being an error). The exit code distinguishes four situations — if `/ct-next` runs inside a `/loop`, this is what decides whether to carry on, stop, or retry later:

| Exit | Meaning | What to do |
|---|---|---|
| `0` | Progress (something was launched, wholly or partially), or there was nothing selectable and it has already been explained why (including the case where the ONLY epic with pending work was excluded by an order collision: the warning above already explains why there is nothing to launch). | Carry on as normal. |
| `1` | Something BROKE or **something was left half-done that a human has to resolve**: a bug, bad configuration, an orphaned issue in `status:in-progress` (see above), an **unmet precondition** (D4: target worktree/branch already occupied, `cmux` absent from PATH, kickoff that does not render, slice with no usable issue number), or (**D5**) at least one slice **launched without verification**: `cmux new-workspace` returned 0 but the session does not appear, or appears in another directory. In that last case the claim is written and the branch and the worktree exist, so there is state to clean up by hand — and it applies **even though other slices of the same batch did launch fine** (before, with one confirmed and one unconfirmed, the batch came out with 0, i.e. "progress"). An order collision NEVER produces this code on its own — it is resolved by excluding the affected epic (a warning), not by aborting. | Stop and let a human look at it — do not retry blindly. For an unverified launch, **look at the cmux session BEFORE deleting anything**: reverting the claim with a live agent is worse than leaving it. The output lists the exact commands. |
| `2` | Usage or static-configuration error: badly placed flags, or a `CT_AGENT_BIN` that is not a bare command. | Fix the invocation. |
| `3` | A batch was selected (from among the epics NOT excluded) but it ended with ZERO launches **and with nothing left half-done**: every candidate was skipped AT CLAIM TIME — collision, cleanly lost race, or an unstable `gh` — typically another concurrent dispatcher getting ahead between this batch's snapshot and the live claim. **No claim written, no branch and no worktree created, nothing to clean up.** This includes the case "one epic was excluded by an order collision AND every candidate of the remaining epics lost the claim race": the exclusion on its own does not move the exit code, it only reduces which epics the selected batch can come from. **D5 narrowed this code**: before, it was also reached with an unverified launch behind it (claim written, worktree created), while the message asserted that nothing had been left half-done and recommended "retry later" — impossible, because the issue was no longer in `status:ready` and the destination was occupied. That case is now `1`. | Retry later (or on the next round of the `/loop`) — it is not an alarm signal, and now the message can assert that truthfully. |

The warnings about order collision, `status:` ambiguity and dependency outside the section do not change any row of this table — they are diagnostics printed before selecting, never a cause of a different exit code.

**No accounts (F35).** The loop no longer evaluates which Claude account dispatches which repo: gone are `ACCOUNT_MAP`, resolution by owner, the `CLAUDE_CONFIG_DIR` that travelled as `--env` to cmux's daemon, the per-account wrappers and the `legacy` map that served to announce reclassifications. Every agent starts with the **ambient configuration** of whoever launches it.

The only knob left is `CT_AGENT_BIN` (default `claude`): the name of the executable that gets typed into the cmux session. It exists because of a measured failure and not out of taste — in a real `.zshrc`, `claude` was a **shell function** that asked «Which account? 1/2», and a login shell resolves the function before any PATH: the agent sat on the `read` forever while **`/ct-next` counted it as launched, with exit 0** (the sentinel is written before invoking the agent, and `command -v` returns 0 for a function). If it happens to you, point `CT_AGENT_BIN` at a non-interactive wrapper.

**`--dry-run` checks what the real run needs (D4):** besides printing the plan, it verifies that `cmux` is on the PATH (without running it), that the agent's binary can be seen from here (only a WARNING: the one that really resolves it is cmux's login shell), that the target worktree and branch `feat/<n>` are free, and that the kickoff renders. The same checks run in the real run **before writing any claim** — before, an already-existing `feat/<n>` was discovered with the issue already claimed. The kickoff is additionally printed in **readable prose** (not just inside the escaped blob of the `cmux` line), which is the only thing that lets you judge the prompt the agent will receive. If there are warnings, the end of the dry run repeats them and makes it clear that it exited 0 **in spite** of them.

**And it shows the WHOLE batch at once (D5).** A `--dry-run` with unmet preconditions still exits `1` (it is never a green light), but it no longer keeps the plan quiet: it prints the block of every selected slice, with each one's problem noted inside its own block, and closes with a summary saying how many failed, **which ones**, which ones have no problems of their own and **which one would break first** in a real run. Before, it exited before printing any block, so with a problem in the second of three you saw neither the kickoff nor the `cmux` line of any of them — exactly what you go to a dry run to look at. The **real** run does not change: it aborts at the preconditions, before writing a single claim. The two check exactly the same thing; the only difference is how much gets printed after having failed.

**Interruption (Ctrl-C / SIGINT / SIGTERM):** `/ct-next` handles the signal — if it arrives just after a claim is confirmed but before the worktree exists, it automatically reverts that claim to `status:ready` before exiting, and exits with the usual signal code (`130` for SIGINT, `143` for SIGTERM) — these TWO codes are reachable in addition to the four in the table above.

**An interruption is ALWAYS acknowledged, even if it arrives late (D5).** Before, a Ctrl-C that arrived with the work already done was discarded **in silence**: with `--cap 1` (this very document's cover invocation), a signal received during a blocking call after the last checkpoint gave `EXIT=0`, `lanzados 1/1` and not one line about the signal — the process finished without ever returning control to the event loop, so the handler never got to run. Now there is a final yield point: the batch summary is printed just the same (it is the real result), and afterwards the signal is explicitly acknowledged, saying that it arrived with the batch already finished, that **nothing is undone** of what was already done, and exiting with `130`/`143`. A technical note, in case this code is touched: that yield point (and the loop's two checkpoints) use `setImmediate`, not `setTimeout` — libuv dispatches signals in the *poll* phase, which runs **after** the *timers* one, so an `await sleep(0)` can resolve without the pending signal having been delivered yet (measured: it failed in 2 out of 8 rounds).

**An honest limit that STILL stands:** if `git worktree add` (or any other blocking call to a subprocess) is genuinely hung and the signal does not reach it, `/ct-next` cannot interrupt it instantly — it bounds it with a timeout (10 minutes by default, `CT_NEXT_CHILD_TIMEOUT_MS`) instead of hanging forever, but that means a Ctrl-C against a real hang can take up to that limit to complete (before this hardening it did not even revert the claim; now it does, however late). When it is **our own timeout** that kills a child, the message says so — with the exact limit and the variable's name — and never presents it as a user interruption.

**Exceptions in the dangerous window (D5).** There was a net for signals but not for exceptions: any unexpected `throw` between the claim and the creation of the worktree left the issue in `status:in-progress` forever, with only a stack dump. Now that case reverts the claim automatically (and if the revert fails, it prints the manual command), without ceasing to show the full trace: it is a bug and it looks like one.

**If the output cannot be written (D5).** The destination of stdout/stderr breaking mid-run (`ct-next | head`, a `/loop` that stops reading) makes log lines get lost — a real limit, with no possible solution — but it does **not** change what `/ct-next` decides nor its exit code. Before it did: with the stdout reader closed, a claim that had been written **successfully** was reported as "unexpected failure […] probably a bug or bad configuration", the batch was aborted and the issue was left orphaned for not having been able to print a line.

The fact that `/ct-next` now DOES call `dispatch-check` does not change the lock's guarantee in itself — it is still the same compare-and-swap-less label mechanism described below. What changes is that, before this, `dispatch-check` was never invoked from the real loop and no issue ever reached `status:in-progress`; now it is invoked, so the warning below stops being a theoretical caveat and starts applying for real on every run.

**Repo conventions that contradict the kickoff (F11, hardened in F14):** before selecting anything, `/ct-next` reads the checkout's `AGENTS.md` and `CLAUDE.md` —**and, one hop away, the repo's own `.md` files that those two cite**— and warns (`[claim]` / `[worktrees]`) if they mandate something different from what the kickoff mandates: their own `dispatch-check.sh`, another worktrees path. The hop is not a luxury: in the real case both guides were clean and the old order was still alive, in the direct imperative to the agent, in the document they themselves called the «full reference». It never blocks: it is diagnostics, like the three warnings above. It matters because the dispatched agent reads those files when it hydrates and is going to obey them: two claim protocols over the same label space end in an issue claimed twice. If reading those files fails for something other than "it does not exist", that is said too — a silence there would be indistinguishable from "there is no conflict". `/ct-init` does the same detection when bootstrapping (`scripts/conventions.js` + `scripts/conventions-io.js`, a single source for both).

A **mandate** is distinguished from a **mention**: the script's name in a directory tree, in a hook inventory table, or in a sentence explaining that the agent no longer does the claim, are not orders and do not warn. And if a signal has already been decided, the repo writes it in `.agent/conventions-ack.md` (`claim: YYYY-MM-DD — motivo`) and that signal —only that one— becomes a one-line note. That is what gives the warning a way out: before F14 the only way to silence it was to delete correct documentation.

**An honest warning about the concurrent claim (T11):** the lock `dispatch-check.mjs` uses to claim an issue (`status:ready` → `status:in-progress`) is GitHub labels, with no compare-and-swap. It is reproduced and verified (not merely suspected) that two dispatchers launched almost at the same time can claim the same shared token (`area:`/`touches:`) and both start — see `scripts/experiments/ac6-race2-deterministic.sh` and `task-11-report.md` §3 for the evidence (3/3 rounds with a real double claim in its most recent run, confirmed against the labels' state in GitHub, and with no exceptions in any run done during its development). There is no wait and no retry that closes this gap today. **The real mitigation is operational: do not launch two `/ct-next` (nor two dispatchers) at the same time against the same repo.** The plan is to migrate the claim to a real atomic primitive (test-and-set via `git refs`); until then, this is the only guarantee that exists.

**The go of the `plan` gate is given ONCE, and on the issue.** After dispatching a slice that carries the `plan` gate (that is, all of them except the ones that opt out with `!plan`), `/ct-next` additionally launches a **detached** process —`scripts/ct-watch-go.mjs`— that polls the issue every 30 seconds, for up to 8 hours, looking for a comment that is **exactly `-OK <nonce>`**, with the nonce of THAT dispatch. When it appears, it locates the slice's cmux session by its title and types into it the line that resumes it (`cmux send` + `send-key`, the same mechanism as the resending of the start-up line). Until this round nobody read that «ok»: work resumed when the same person went to the cmux window and pushed it by hand, so the permission was given twice and the one that counted was not the one that stayed written. `/ct-next` draws the nonce when dispatching and **dictates it on screen** (`GO de #N: contesta exactamente …`); the watcher is only passed its `sha256` via `--go-hash`, because a process's argv is shown by `ps` and its log is a readable file. It prints its pid and its log's path, which lives **outside the repo** (`~/.claude/control-tower/log/watch-go-<issue>.log`, next to the telemetry and for the same reason) and which is opened by the watcher itself, not by `/ct-next`. It is only launched if the slice **counted as launched**: the watcher's only handle is the session's title, so on the two paths where cmux does not locate it (`not-found`, `wrong-cwd`) launching it would be announcing «the session starts on its own» in the same run that says that session cannot be found.

Three things worth knowing about it. **Exact match**: the go with anything after it starts NOTHING, and a **bare** `-OK` —with no nonce— does not either, on purpose — an unrecognised token leaves you waiting and you notice, whereas one recognised too generously would start exactly the work that whoever wrote «-OK but change the name» wanted to hold back. **Only what was not there when it started counts** — the window is the identifiers of the comments that already existed, not a cut-off date: `createdAt` is set by GitHub's server and the cut-off would be set by your machine's clock, and with those two clocks in disagreement an inherited `-OK` could fall inside the window or a legitimate one could fall outside it forever. That way, an `-OK` inherited from an earlier dispatch of the same issue does not skip the gate in silence — and since the go carries a nonce, that property is additionally held up by the nonce itself, which is why `--release` can look at the whole issue with no window. And **it shuts itself down if the session disappears**: if you close the slice's window or its agent dies, there is nobody to deliver the go to and the watcher terminates (exit 4) instead of polling GitHub for hours. Mind the distinction, because it matters: it only shuts down if cmux **answers** that it is not there; if it could not be *asked* (daemon down, timeout) it retries, also with the go already seen. If it could not be launched, a warning is issued and the dispatch carries on: the slice is already under way and what is lost is the automation, not the work — you will have to push the session by hand after giving the go, as before.

The deadlines are adjusted with `CT_WATCH_GO_POLL_MS` and `CT_WATCH_GO_TIMEOUT_MS`; a value that is not understood aborts the watcher instead of falling back to the default in silence. **What this mechanism does NOT do**: it does not accept `-REVIEW` or any way of requesting changes by comment (the terminal is still there for that), it does not comment on the issue to explain formats, and **there is no sentinel proving that the session received the line** (the only thing that is known, and the only thing the log asserts, is that `cmux send` and `send-key` returned 0 — a real sentinel would require the agent to write something, that is, depending on the very agent it is being handed to).

**The guardrail on the go, built (F38).** Until `0.41.0` this had a hole written down right here: the agent has `gh`, so it could write `-OK` on its own issue — and with the `plan` gate implied by default on every slice, that was a door that the gated party opened, leaving on top of it the record of a human review that never happened. It is closed in two halves:

1. **The go carries a per-dispatch nonce.** `-OK <nonce>`, 8 hex characters drawn at dispatch time. The nonce comes out on the screen of whoever dispatches and nowhere else: it is not in the kickoff, nor in the issue, nor in the worktree, nor in the watcher's argv, nor in its log — its `sha256` travels there. The commitment is recorded **outside the repo**, in `~/.claude/control-tower/go/<owner>__<repo>-<issue>.json`, because everything that lives on GitHub is written by the agent.
2. **`--release` requires it.** `dispatch-check --release` refuses with **exit 9** —the last gate on the ladder, mutating nothing— if the `plan` gate is standing and no comment on the issue carries that dispatch's go. Before, nothing required it: an agent could ignore the whole gate and deliver anyway, because the kickoff that tells it to stop is a prompt. An unreadable record or comments that cannot be read also hold it back: this mechanism does not assert clean what it has not been able to look at. An explicit opt-out (`gate:none`, or `!plan` in the `Gate` column) releases without looking at anything; an issue that declares **no** gate does not, because silence is not an opt-out.

**If the nonce is lost** (you closed the session, it was dispatched yesterday): `node <plugin>/scripts/ct-go.mjs --issue N --repo owner/name` draws a new one, rewrites the commitment —the previous one stops being valid in the same act— and dictates it. It does not relaunch the watcher, so after answering you will have to push the session by hand, as when the deadline expired.

**And the limit, said out loud.** By default the nonce comes out on `stdout`, which when `/ct-next` is run by a Claude session is also that session's context: the guardrail protects against the **implementing** agent —the one working in the worktree, the one with the verdict at stake— and not against the coordinator, which is already a trusted party in everything else. With `CT_GO_CHANNEL=notify` the nonce goes out through a system notification and does not enter any agent's context (it is not the default because it is a channel that may not exist: no GUI, over ssh, without permissions). And fundamentally, agent and coordinator run with the **same uid on the same machine**: none of this is cryptography against an adversary, it is a door that no longer opens by accident or in passing. Forging the go stops being «a `gh issue comment` on my own issue» and starts requiring you to manipulate the coordinator's private state, which is the line behind which every other gate already sits. Closing it completely requires a verifier that does **not** run under that uid —CI, or another identity—, and that remains named and unbuilt.

**The merge does not need an errand either (`ct-watch-merge`).** Gate 3 is human, and until now merging produced **no mechanical signal**: the PR got merged, the issue got closed, and the harvest of F20's paragraph —`.worktrees/<n>`, `feat/<n>` and its live `claude`— stayed on disk until the same person who had merged went to the coordinator's window to tell it. The event was on GitHub; what triggered the harvest was an errand.

It is launched by **`dispatch-check.mjs --release`**, not by `/ct-next`: that is the exact instant at which there is an open PR waiting for a human merge, whereas launching it at dispatch time would put a process asking about a PR that does not yet exist for the whole implementation. `scripts/ct-watch-merge.mjs` polls `gh pr list --head feat/<n> --state merged` every **60 seconds, for up to 48 hours** (`CT_WATCH_MERGE_POLL_MS` / `CT_WATCH_MERGE_TIMEOUT_MS`, with the same abort on a value that is not understood as the `-OK` watcher's) and, when it sees it merged, types into the coordinator a line naming **the PR, the slice and the two artefacts** left on disk. It prints its pid and its log's path, `~/.claude/control-tower/log/watch-merge-<issue>.log`, which the watcher itself opens.

**THE RULE OF USE, because without it this does not work: the coordinator session has to be a cmux workspace open IN THE MAIN CHECKOUT of the repo it coordinates.** The watcher locates it by its `current_directory`, and not by its title, because there is no title to derive: a slice session's title is computed by the loop itself (`dispatch.js#cmuxSessionName`, a pure function that `/ct-next` uses to create it and the `-OK` watcher to find it), whereas the coordinator **is not created by the loop — you open it**, in whichever window you fancy. The directory is the only observable property left.

Measured in the field on 2026-08-26 with PR #16 of `jjponz/rust-monitoring`: the merge was seen 34 seconds after it happened and there was nobody to tell, because the window of whoever was coordinating was open in another repo. The watcher did the right thing and said so; the defect of that episode was that this rule **was written nowhere**. It was decided to keep the inference and write the rule, instead of building a registry where the coordinator announced itself: that would be new state, with its expiry and its «is that still alive?», for a single consumer.

**You can opt out of it, and it is declared: `--release --no-watch-merge`.** It is asked for by a flow that has no coordinator session —the companion app holds the terminal, so the main checkout's only cmux workspace is the server's that dispatched—, and without the flag the watcher does the only thing it knows: it locates by directory, finds that tab, types at a program a paragraph written for an agent, and its log announces it as delivered. A false delivery in writing is worse than not warning. **It is not detected, it is declared**: from `--release` there is no way of telling a coordinator from a server, because both are a cmux workspace in the same directory; whoever dispatches does know. The flag **relaxes none of the five gates** and does not change the label's movement: the only thing lost is the moment of the warning, and that is recovered by the `cosecha pendiente:` of the next `/ct-next`. It is said on stderr when releasing, so that the silence is not read as a watcher that is in fact there.

**It does not shut down because the coordinator is absent**, and there it diverges on purpose from the `-OK` watcher. But mind what that divergence buys and what it does not: it buys surviving an absence **while it waits** (you close the window, you reopen it, the watching goes on), and it does **not** buy an absence **at the moment of delivering** — if there is no coordinator on that tick, the warning is lost, it is said, and it exits with 1. And the lost warning is not a hole: `/ct-next` keeps emitting `cosecha pendiente:` on every run, so it degrades to the old mode —you find out the next time you dispatch— and not to nobody ever finding out. What this watcher contributes is not the knowledge, which already existed: it is **the moment**. And it **deletes nothing**: it warns, and the harvest is collected by the coordinator, with F20's decision intact — «merged» is not «nobody is touching that». With `--dry-run` it is not launched (nothing has been moved, so there is no merge to wait for), and if it cannot be launched a warning is issued and **the release is still a success**: the work is already delivered and what is lost is the automation, not the delivery. There is no sentinel here either — the only thing the log asserts is that `cmux send` and `send-key` returned 0.
